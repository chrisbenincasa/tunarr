Every entry here shares one shape. Something goes wrong, and the system returns success. A backup reports completion without writing a file. A partial settings update resets the fields it omitted. A cache invalidation matches no query. A scheduler hands back a channel that plays nothing for three days and logs not a word.

That shape is why the reported bugs were hard to trace: the logs are clean precisely because the failures are silent. It is also why they cluster — the same habits produce them, so finding one reliably predicts where the next one lives.

Time-slot scheduler

8 findings · 2 critical

Traced from one user report: a slot at offset 107400000 — 29h 50m — in a daily schedule. Probing the scheduler's other unguarded inputs turned up worse.

TS-1

A slot offset beyond the period kills the schedule

Critical Reproduced Fixed · #2012

server/src/services/scheduling/TimeSlotService.ts:183, :210, :253

The scheduler reduces its cursor modulo the period but never the slot: currOffset = totalOffsetMs % periodMs is compared against a raw slot.startTime. An offset at or past the period therefore matches no cursor position at all. That asymmetry is the whole bug.

Which failure you get depends on the time of day the schedule is generated:

Generated atResult
00:00 – 05:45throws “Could not find a suitable slot”
05:50 – 23:551 lineup item — a single 48–72h flex block

With the reporter's settings — 5-minute pad, 10-minute lateness — 70 of 288 five-minute start times throw, 24% of the day. The rest return a channel that plays nothing. A control slot inside the period never throws at any of the 288, and produces 32 items with a longest block of 1.5h.

Fixed

Normalize startTime into the period at schedule time so values already on disk heal themselves, plus a strict request schema (TS-8) so new ones cannot be created. Four tests; the strongest asserts that a slot at t and one at t + period schedule identically — before, they produced 33 items or 1.

TS-2

A fractional offset hangs the worker thread permanently

Critical Reproduced

server/src/services/scheduling/TimeSlotService.ts — scheduling loop

startTime: 1234.567 sends the scheduler into a loop that never advances. Because the loop is synchronous despite the enclosing async, it blocks the event loop outright: the test runner's own 15-second timeout never fired and the process had to be killed at 60 seconds.

Nothing can interrupt it. The worker pool's timeoutPromise rejects the caller's promise after 60s while the thread keeps burning a core forever, so N such requests permanently exhaust an N-worker pool. It passes the current schema, because startTime is a bare z.number().

Fixed at the boundary

Rejected by the strict request schema (TS-8). The loop itself is unchanged and would still hang given a fractional value arriving by any other route.

TS-3

A pad of zero returns a lineup of NaN durations

High Reproduced

padMs: 0 makes the cursor's modulo NaN. The scheduler completes and reports success, handing back 32 lineup items whose durations are all NaN. No error, no warning.

TS-4

A non-positive horizon silently yields an empty or half schedule

Medium Reproduced

maxDays: -1 returns zero lineup items and reports success. maxDays: 0 returns 16 items where 32 are expected. Both pass the schema.

TS-5

An empty slot list reports the same error as a broken one

Medium Reproduced

A schedule with no slots throws “Could not find a suitable slot” — the identical message produced by TS-1. Two unrelated causes, one string, so the log cannot tell them apart.

TS-6

Normalizing collides two slots, and the loser depends on array order

High Reproduced Fixed · #2012

Found by review of the TS-1 fix, not in the original code. Reducing offsets into the period maps 05:50 and 29:50 onto the same value. Equal offsets give the earlier slot a zero-width window — endTime equals its own startTime — so it airs nothing, and which of the two dies depends on storage order:

Slots, in array orderBeforeAfter
A@05:50, B@29:50A droppedA wins
B@29:50, A@05:50B droppedB wins
Fixed

Collisions collapse explicitly, keeping the first — the same rule the editor already uses when converting a weekly schedule to a daily one. Had the server kept the last instead, what airs would not match what the editor displays.

TS-7

The server's OneDayMillis is one week

High Read-only

server/src/ffmpeg/builder/constants.ts:238

export const OneDayMillis = 7 * 24 * 60 * 60 * 1000;   // 604800000
export const FiveMinutesMillis = 5 * 60 * 60 * 1000;   // five HOURS

Used as a day in four live places — StreamProgramCalculator.ts:329 (offline lineup item duration) and :603 (stream duration for an empty lineup), plus three sentinel uses in FillerPickerV2.ts. The two stream-duration uses produce week-long blocks where a day was intended. FiveMinutesMillis is 60× too large but has no callers.

The codebase now holds three OneDayMillis definitions: two correct in web, this one wrong on the server.

TS-8

Every schedule field was an unbounded number

High Fixed · #2013

types/src/api/TimeSlots.ts — StrictTimeSlotScheduleSchema

latenessMs, maxDays, padMs and startTime were all bare z.number(), and slots had no minimum length — which is how TS-1 through TS-5 all reached the scheduler.

The obvious fix was wrong. TimeSlotScheduleSchema also feeds LineupScheduleSchema inside CondensedChannelProgrammingSchema, a persisted and response schema. Tightening it would make any channel already holding a bad value fail response serialization and stop loading — worse than the bug. So the bounds live in a strict request-only variant, mirroring the existing StrictChannelIconSchema split, with a test asserting the permissive schema still accepts every rejected case.

Where the bad slot comes from

5 findings

The reported value decomposes exactly: 107400000 = 05:50 + 1 × OneDayMillis. Two controls in the editor combine to produce it, and a third hides the result.

FE-A

“Add slot” advances an hour at a time with no wraparound

High Fixed · #2014

web/src/components/slot_scheduler/AddTimeSlotButton.tsx:35-37, :53-57

const maxSlot = maxBy(relevantSlots, (p) => p.startTime);
const newStartTime = maxSlot
  ? dayjs.duration(maxSlot.startTime).add(1, 'hour')   // no modulo
  : ...

In a daily schedule the “relevant slots” filter is a no-op — it returns true for every slot whenever the period is not week — so each click walks the global maximum upward without limit. Building an hourly day takes 24 clicks; the 25th lands on exactly 24h. That is the ordinary way to build an hourly schedule, not an exotic sequence.

FE-B

The time picker preserves a day multiplier that only means something weekly

High Fixed · #2014

web/src/components/slot_scheduler/EditTimeSlotDialogContent.tsx:162-164

const multiplier = Math.floor(getValues('startTime') / OneDayMillis);
originalOnChange(millis + multiplier * OneDayMillis);

Applied unconditionally. Take the 24h slot from FE-A, set it to 5:50 AM, and the multiplier of 1 survives: 21000000 + 86400000 = 107400000. Exactly the reported value.

FE-C

The control that would reveal the extra day is hidden

Medium Read-only

web/src/components/slot_scheduler/EditTimeSlotDialogContent.tsx:330

The Day dropdown renders only when currentPeriod === 'week'. In a daily schedule the slot displays as an ordinary “5:50 AM” with no affordance to see or clear the extra day — so the state is both invisible and uncorrectable from the editor.

FE-D

The editor normalizes on read but not on save, so the evidence self-destructs

Medium Read-only

web/src/pages/channels/TimeSlotEditorPage.tsx:119-121 (read) · :187 (save)

convertToViewModel applies % OneDayMillis when loading a schedule; onSave spreads getValues() with no normalization. So a bad value can only be created and saved inside a single editing session — and reopening that channel and saving again silently repairs it.

This is why the bug resists reproduction after the fact, and it is worth asking the reporter whether they have touched the schedule since filing.

FE-E

Switching a daily schedule to weekly multiplies a bad value across seven days

Medium Read-only

web/src/pages/channels/TimeSlotEditorPage.tsx:264

startTime: slot.startTime + offset across seven offsets. It cannot originate the bug — the reverse conversion does apply a modulo — but it replicates an existing bad value seven times.

FE-4

Creating and deleting a channel invalidate a cache key that matches nothing

High Reproduced Fixed · #2018

hooks/useCreateChannel.ts:14 · pages/channels/ChannelsPage.tsx:164 · helpers/queryUtil.ts:9

Two query-key conventions coexist. The generated client builds keys whose first element is an object carrying tags — thirteen queries are tagged Channels. But both call sites above invalidate with the plain string key ['Channels'], and TanStack matches keys structurally by prefix. They match nothing.

queryKeySchema also declares tags as .optional(), so an object key with no tags parses cleanly and then intersects to zero — a second fail-open in the same nine lines. Masked on navigation by staleTime: 0, but not while the list stays mounted, which is exactly where the delete mutation lives.

Five further mutation files invalidate nothing at all, including the slot save path hooks/slot_scheduler/useScheduleSlots.ts.

KEY

The discovery that generalized: .partial() keeps .default()

High Verified

Zod's .partial() wraps a field's .default() rather than removing it. So a request schema built with .partial() silently substitutes defaults for fields the caller omitted — which is how a partial settings update reset the settings it never mentioned. No handler-side ?? stored could have fixed it; the cause was one layer up.

A 200-line walker over the _zod.def tree now audits 28 request schemas for four contract-breaking constructs, with an allowlist that fails if an entry stops matching. It independently rediscovered a known bug, which is what validated the detector.

Build tooling

4 findings · all fixed
TL-1

The lint gate linted the whole repository, or nothing at all

High Fixed · #2011

package.json — lint-changed

eslint --fix $(git diff --name-only HEAD -- './**/*.ts*' | xargs)

Three defects in one line. With a clean tree the subshell expands to nothing, so eslint receives no paths and lints the entire monorepo until the V8 heap aborts — and because --fix rewrites files as it goes, it reformats whatever it reached on the way down. Deleted paths were passed straight through and killed it. And since a clean tree produced an empty list, the gate reported success on a branch full of changes.

It failed exactly when you ran it after committing, which is the normal moment to run a final check.

Fixed — and the first fix was wrong too

Scoping to the merge-base with main meant --fix would rewrite 202 files on infinite-schedules and 735 on an older branch. Default scope is now the working tree; branch scope moved behind an explicit --branch flag that announces its file count first.

TL-2

No local command covers what CI checks

High Reproduced Fixed · #2011

.github/workflows/ — main.yml, lingui-pr.yml, commitlint.yml

This one was found by hitting it. #2014 went up after a clean turbo typecheck and a clean test run, and failed CI anyway. The gates are spread across three workflows and no local command runs them together:

GateWorkflow
turbo typecheck --filter=@tunarr/servermain.yml
turbo build --filter=@tunarr/webmain.yml
turbo test -- runmain.yml
lingui extract + git diff --exit-codelingui-pr.yml
conventional-commit checkcommitlint.yml

The failure was an import block growing five lines, which shifted the source-line references lingui writes into the .po catalogs. No message changed — 957 strings before and after — but git diff --exit-code does not care. Running the full turbo build would not have caught it either; the check does not live there.

Two gaps worth naming separately. CI never runs eslint at all — the pre-commit hook is its only enforcement, so a commit made with the hook bypassed reaches the PR unlinted. And the lingui catalogs are a generated artifact checked in as source, so any edit that moves a line in a file containing a translated string silently invalidates them.

Fixed — pnpm preflight

One command runs all five gates plus eslint and prints a single summary rather than stopping at the first failure. The lingui gate leaves the regenerated catalogs applied, since regenerating them is also the remedy, and names the files to commit. Verified by replaying it against the exact stale-catalog state that broke #2014: it fails, and passes once the catalogs are committed.

TL-3

Web test files have never been typechecked

High Reproduced Fixed · #2017

web/tsconfig.build.json — exclude

tsconfig.build.json excludes ./src/**/*.test.ts(x), and it is the only config CI typechecks web through — turbo build --filter=@tunarr/web runs tsgo -p tsconfig.build.json. Checking with the config that does include them reports 14 errors across 4 of the 11 web test files: fixtures carrying persisted, uniqueId, subtype and a top-level title, none of which exist on ContentProgram.

useAddBreaks.test.ts is the clearest: its fixture has no program field at all, and its assertions read a title the fixture itself invented. The tests pass, against a shape nothing in the app can produce — and these are four of the five pure-function tests this plan calls “the pattern that already works.”

TL-4

The pre-commit hook invalidates the catalogs the preflight just certified

Medium Reproduced Fixed · #2011

.husky/pre-commit → lint-staged

Found by the tool failing on its own author, twice. lint-staged runs prettier --write and eslint --fix on staged files at commit time — after any preflight can possibly run. So a tree that passed the lingui gate gets reformatted during git commit, shifting the source line numbers the catalogs record, and the PR goes red for catalogs certified moments earlier.

Reordering gates inside the preflight does not fix this on its own. The preflight now applies the same prettier pass the hook will, so the hook has nothing left to change.

Sweep S1 — dead cache invalidations

11 sites · 1 cause · fixed

The first mechanical sweep the plan proposed, and the cheapest. Walk every query key used to register a query against every key used to invalidate one. FE-4 was the known instance; the sweep found ten more, all the same mistake.

S1

A hand-written string key can never match a generated one

High Reproduced Fixed · #2018

11 sites across hooks/, pages/ and components/

Generated hey-api keys are a single-element array holding an object — [{ _id, baseURL, tags }]. TanStack matches by structural prefix, so a hand-written string key diverges at element 0 and matches nothing. The call resolves, logs nothing, and the cache stays stale. The give-away is the literal ['Channels']: Channels is the endpoint tag, not a key segment.

SiteWhat stayed stale
useCreateChannelnew channel absent from the list

XmlTvSettingsPagesettings cache stale after save
SystemDebugPage ×3env / nvidia / vaapi checks inert on reclick
TvGuideignores xmltv regeneration events

useScanNow had two stacked bugs: its predicate compared a Query instance against a key array, and one operand was an options object rather than a key. TvGuide carried a // Gnarly comment — the author knew. ChannelDeleteDialog already did it correctly, so the app had two channel-delete paths that behaved differently.

The fix nearly repeated the bug

Invalidating by tag is the right mechanism, but picking a tag is not automatically safe. The TV Guide fix nearly shipped against the Guide tag — which belongs to /api/guide/channels, endpoints that page never calls. It renders from the channel lineup endpoints, tagged Channels. That would have replaced one dead invalidation with another. The tests are therefore table-driven and pin every site to the query it must refresh, driving a real QueryClient rather than reimplementing the matcher.
